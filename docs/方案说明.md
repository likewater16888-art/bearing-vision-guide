# 成品轴承视觉检测设备 · 调试速查站 方案说明

> 版本 v1.2 ｜ 2026-11-10 ｜ 数据源《成品轴承操作手册细化版本.docx》（519 节 / 355 图）

## 1. 一句话方案

把一份 85 MB、按"章节顺序"组织的手册，重排成按"现场问题"组织的**单页速查站**：不改一行设备代码，不引入任何框架或服务端，双击 `web/index.html` 就能在 3 秒内定位到"缺陷 → 阶段 → 相机 → 参数 → 调整方向"，并且每条结论都能一键回到原文核对。

## 2. 背景与痛点

手册本身写得细，但**结构是"文档结构"，不是"使用结构"**：

| 现场问题 | 在手册里要怎么办 |
| --- | --- |
| 端面凹陷现在漏检，先看哪一步？ | 先找"端面"章节 → 再翻阶段划分 → 再找跑马灯 → 再找参数表，跨 4 处、翻 20 多页 |
| 内径识别区域偏移过大，是误判还是定位失败？ | 现象描述在案例段，参数解释在参数章，处理动作在流程章，三处分散 |
| 6 工位机型和 8 工位机型有什么区别？ | 差异散落在相机分工、阶段数、参数表，靠读者自己拼 |
| 新人培训从哪开始？ | 手册是"参考书"体例，缺一条最短路径 |

同时手册是 **.docx**：不能站内搜索、不能在手机上看、发到群里会被转发成旧版本、图片要滚很久才能对上文字。

**因此本项目不是"把 docx 转成网页"，而是"重新做一次信息架构"**：保留全文用于核对，另建一层结构化结论用于现场查。

## 3. 目标与非目标

**目标**

1. **3 秒定位**：任何一个现场提问，最多 2 次点击 / 1 次搜索到达答案。
2. **结论先行**：先给区间、方向、动作，再给依据；不在现场读长段落。
3. **可核对**：结构化结论旁必须有「手册原文 →」入口，落到对应一级章节。
4. **零门槛分发**：单个文件夹拷走即可用；无需安装、无需网络、无需账号。
5. **可维护**：手册更新后重跑两条命令即可重建，且有一致性自检兜底。

**非目标**

- 不做设备控制、不做数据采集、不做 MES 对接。
- 不做多人协作编辑、不做权限与审计。
- 不追求"手册全文的完美还原"（版式细节以 docx 原件为准）。

## 4. 使用场景与角色

| 角色 | 典型任务 | 主要用到 |
| --- | --- | --- |
| 产线操作工 | 换型后确认阶段数 / 检测张数；报警后先做哪三步 | 速查、专题（跑马灯、定位三步排查）、开线点检 |
| 设备巡检 / 调试员 | 判断是漏检还是误判；把参数从 A 调到 B | 速查（阶段成像核查、参数区间）、案例库、参数释义 |
| 工艺 / 品质 / 培训 | 复盘异常、做培训材料、核对口径 | 案例库、专题、产品阶段矩阵、全文 |
| 新人 | 从零建立"工位—阶段—参数"的心智模型 | 速查首屏 → 标准调参流程 → 案例库 |

关键场景验收句：**"站在机台前，一只手拿手机或鼠标，另一只手在调参数"** —— 所有布局、字号、信息密度都为这个姿势服务。

## 5. 信息架构

### 5.1 两条主轴 + 一个全文兜底

```
工位（外径 / 内径 / 端面）  ×  机型（8 工位标准 / 6 工位紧凑）
        │
        ├── 阶段（光源、采图张数、亮度锚点、检测项、禁止画面、亮度怎么调、风险）
        ├── 教学层（亮度调校总则、灰度链路、检测项逐项、型号 × 阶段矩阵、现场问答）
        ├── 参数（区间、步长、调整方向）
        ├── 流程（标准调参步骤）
        ├── 坑（现场常见错误）
        └── 案例（现象 / 根因 / 动作 / 截图）

全文（519 节）—— 只在"要原话、要条款、要表格"时进入
```

### 5.2 六个视图的职责边界

| 视图 | 心智模型 | 不该放什么 |
| --- | --- | --- |
| 速查 | "这个工位现在怎么调" | 长篇原理、跨工位对比 |
| 专题 | "这个动作的固定套路" | 与工位绑定的细节（应回速查） |
| 案例 | "这个现象别人怎么解决的" | 通用原理（应在专题/速查） |
| 参数 | "这个参数调到多少" | 案例分析 |
| 全文 | "手册原话/原表" | 任何再加工结论 |
| 学 | "我记住了吗、能不能考过、哪一维弱" | 查得到的结论（速查已覆盖）、原文条款（全文已覆盖） |

**为什么参数要单独成视图**：现场最高频的问题是"这个值调到多少"。参数在手册里分散在每个工位的表格中，单独抽出 32 个关键参数按算法体系分组，配"合理区间 + 含义 + 调整方向"，把"查表"变成"查词典"。

## 6. 数据模型

数据和视图严格分层：**知识层**（人写）、**全文层**（机器抽）、**图片层**（机器生成）。三层都是普通 JS 全局变量，`<script>` 直接引入即可，完全避开 `fetch` 与 CORS，因此 `file://` 可用。

### 6.2 全文层 `window.MANUAL_DOC`（`web/data/manual.js`，机器生成）

```js
{
  meta: { source, generated, sections: 519, images: 355 },
  sections: [{
    id: "s070",           // 顺序编号，稳定可引用
    level: 1,             // 1–9（按 docx 大纲级别）
    title: "五、外径",
    path: "封面与目录 / 四、型号管理 / 五、外径",   // 面包屑
    body: [
      { t: "p", text: "…", img?: "images/xxx.webp" },
      { t: "img", src: ["images/a.webp"], cap: "" },
      { t: "table", rows: [[{ text: "…", img?: ["images/b.webp"] }]] }
    ]
  }]
}
```

`id` 由生成顺序决定（`s001`…），**不要在正文里硬编码**；知识层引用章节用 `stations[].sections`，页面里的「手册原文 →」通过一级标题匹配得到目标 `id`。

### 6.3 图片层 `window.IMG_INDEX`（`web/data/images.js`）

```js
{ "291": "images/p0291-rId17.webp", … }   // 手册图片序号 → 相对 web/ 的路径
```

案例、阶段配图只存序号，不存路径：图片重新生成（改名、换格式）时知识层不用改。

### 6.4 教学层 `window.LEARN`（`web/data/learn.js`，由 `tools/build_learn.js` 生成）

| 字段 | 数量 | 关键字段 | 说明 |
| --- | --- | --- | --- |
| `courses[]` | 26 | `id` / `no` / `title` / `sub` / `intro` / `mins` / `sec[]` / `kp[]` / `qn` / `dims` | 课程 = 手册章节切片，`sec[]` 覆盖手册全部 519 节（合计 519，无跨章重合）；`dims` 是六维知识点计数，用于抽考补学清单 |
| `kps{}` | 701 | `t` / `dim` / `c` / `f[]` / `img[]` / `sec` / `src` | 知识点 = 手册小节（519，逐节一条，结论句直接截自原文）+ 结构化条目（182：参数 / 检测项 / 亮度锚点 / 流程步 / 陷阱 / 红线 / 术语 / 型号矩阵 / 案例 / 阶段）；`src` 标明来源类型，`dim` ∈ A–G |
| `cards[]` | 701 | `k` / `f` / `b` / `img` | 抽认卡，正反面都可回到 `kps[k]`；复习间隔用 box 0–5（0/1/3/7/16/35 天） |
| `quiz[]` | 708 | `id` / `kp` / `type` / `dim` / `q` / `opts[4]` / `a` / `why` / `sec` / `img` | 519 道小节题（图题 95 / 数值填空 21 / 归属题）+ 189 道结构化题；`type:"img"` 表示图片判读题 |
| `coverage` | — | `sections` / `secKp` / `secQuiz` / `kps` / `quiz` / `cards` / `dims` | 自检脚本据此核对「手册覆盖率 = 100%」与数量基线 |

派生规则（保证「不编造」）：

1. 小节知识点只取手册原文句子，优先带数字 / 必须 / 禁止 / 判据的句子；句首是"展开 / 同时 / 另外"等承接词时舍弃（脱离上下文有歧义）。
2. 纯图片小节（只有标题、没有正文）不问"出自哪节"，改问"归属哪个部分"，答案取 `path` 的父级标题。
3. 干扰项一律从同章节其他真实结论里取，去重按「去空白 + 去括号」归一化后比较，避免同义重复选项。
4. 每题都带 `why`（判据 / 原文），答错后可直接跳 `sec` 看原文。

学习进度存在浏览器 `localStorage["bearing.learn.v1"]`，结构：`{ kp:{id:{b,due,n,r,w}}, wrong:{quizId:1}, course:{cid:{a,r,best}}, exams:[{ts,score,dims,n,r}], days:{yymmdd:题数} }`。

## 7. 内容管线：docx → 可查询数据

### 7.1 三步流水线

```
成品轴承操作手册细化版本.docx
      │  python tools/extract_docx.py        （解包 + 解析 + 图片重编码）
      ▼
tools/extracted/
      ├── manual.txt         带 [H1]/[H2]/[TABLE]/[IMG] 标记的纯文本（便于人工抽查）
      ├── blocks.json        段落 / 表格 / 图片的结构化块序列
      ├── images/*.webp      正文图片（max-width 1200, quality 82）
      └── image_map.json     rId → 文件名 + 尺寸
      │  python tools/build_web_data.py      （分节 + 转 JS 变量 + 拷贝图片）
      ▼
web/data/manual.js  web/data/images.js  web/images/*.webp
      │  node tools/build_learn.js            （派生知识点 / 卡片 / 题库，生成 learn.js）
      ▼
web/data/learn.js
      │  node tools/check_web_data.js  +  node tools/check_learn_data.js  （一致性自检）
      ▼
web/index.html（浏览器渲染）
```

教学数据是**派生层**，不是第二个手写知识库：题库的正确答案必须能在 `manual.js`（小节题）或 `knowledge.js`（结构化题）原文里逐字找到，`check_learn_data.js` 逐题校验，找不到直接退出码 1 —— 这就是「不许编题」的硬闸门。

### 7.2 解析规则（为什么不用现成 docx 库）

手册 85 MB、图片极多，且版式是"大纲级别 + 段落 + 表格"，直接对 `word/document.xml` 做正则 + 结构化切分比引依赖更可控：

| 元素 | 处理方式 |
| --- | --- |
| `w:p` + `w:pStyle` | 按 `Heading N` / 自定义样式映射到 `level`（1–9），无样式的按正文 |
| `w:tbl` / `w:tr` / `w:tc` | 逐格抽取文本；单元格内的 `r:embed` 收进 `img[]` |
| `r:embed` / `w:drawing` | 替换为占位符 `[[IMG:rId]]`，后续由 `image_map.json` 换成文件路径 |
| 表格内图片 | 保留在单元格内，全文视图渲染为单元格中的缩略图 |
| 图片 | Pillow 等比缩到宽 ≤1200 并转 webp（体积从 85 MB 降到可秒开） |

**已知失败模式与兜底**：合并单元格可能被拆成多行；文本框 / 艺术字内容会丢；编号列表的层级可能压平。因此管线产出的 `manual.txt` 必须保留给人抽查，且知识层的关键结论**一律手写**，不从自动抽取结果里"猜"。

### 7.3 为什么知识层要手写

手册写的是"是什么"，现场要的是"先看哪、调到多少、调错了会怎样"。这层判断无法自动生成，也不应该自动生成——它是本方案的核心资产。自动抽取只负责两件事：**全文可检索**、**图片可对照**。

教学层（v1.3）是例外，但**只例外一半**：题目考的是"这句判据出自哪节 / 这个参数区间是多少 / 这张图属于哪个检测项 / 这个案例的根因是什么"，答案一律来自上面两层原文；凡是"该怎么办"的判断，仍然只从手写的 `knowledge.js` 出。因此题库可以脚本派生，但派生结果必须过 `check_learn_data.js` 的"答案可回原文"校验。

## 8. 前端实现

### 8.1 技术选择

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 框架 | 无（原生 DOM + 模板字符串） | 单页、只读、无状态同步问题；避免构建链与 CDN 依赖 |
| 数据加载 | 三个 `<script>` 全局变量 | `file://` 下 `fetch` 会被 CORS 拦，`<script>` 不受限 |
| 路由 | `location.hash` + `hashchange` | 与静态托管天然兼容，可直接分享到聊天工具 |
| 样式 | 单一 CSS + CSS 变量（设计 token） | 深色模式、打印、响应式只需覆盖变量与少量媒体查询 |
| 构建 | 无 | 改完存盘刷新即生效，现场也能改 |

### 8.2 渲染管线

```
init()  →  填充机型下拉  →  buildIndex()  →  parseHash()  →  renderAll()  →  bind()
renderAll()  →  renderSide()（左侧导航，随视图变化）
             →  quickView / guideView / caseView / glossView / docView（返回 HTML 字符串）
             →  view.innerHTML = html + 页脚（数据源 / 版本 / 节数 / 图片数）
```

- 所有视图函数**只返回字符串**，不直接操作 DOM（除 `renderAll` 统一赋值），便于整体替换与调试。
- 所有用户数据经 `esc()` 转义后插入，避免手册文本里的 `<` `&` 破坏结构。
- 事件用**一个 document 级委托**处理（`data-tab` / `data-station` / `data-guide` / `data-case` / `data-doc` / `data-gloss` / `data-product` / `data-route`），重渲染后无需重新绑定。

### 8.3 搜索

```
输入 → 归一化（小写 + 去空白） → 空格分词 → 每个 token 必须命中（AND）
     → 打分：标题命中 +6 / 副标题 +3 / 正文 +1，连续子串额外加分
     → 取前 12 条 → 生成 snippet（首个命中位置 ±40 字）→ <mark> 高亮
```

索引内容 = 知识层全部对象（工位 / 阶段 / 参数 / 坑 / 产品 / 专题 / 案例）+ 手册 519 节正文，扁平化后量级为几十万字，纯内存过滤，输入无延迟。

### 8.4 机型切换

`state.machine`（`m8` / `m6`）影响：相机分工显示、端面阶段数、产品矩阵阶段表、侧栏相机编号。值写入 `localStorage`（`kb.machine`），隐私模式下 try/catch 静默降级。

## 9. 交互与视觉

**三条硬规则**

1. **首屏即答案**：速查页第一屏必须是"算法 / 光源 / 相机 / 缺陷 + 阶段熔断句"，不放大标题和引导文案。
2. **颜色只表达语义**：`--accent` 仅用于可点击与当前态；`--warn` 用于风险后果；`--danger` 用于红线与"100% 漏检"级别结论。不做装饰性配色。
3. **正文可读优先**：15px / 1.7，表格数字用等宽字体（`--mono`）并对齐，避免"0.50 ~ 0.75"被换行拆开。

**组件清单**：顶栏（品牌 + 搜索 + 机型）、结果浮层、分段 Tab（5 等分）、侧栏树（`lvl1/2/3` 缩进）、卡片、键值表（`dl.kv`）、参数表、阶段块（标签 chips + 亮度锚点框 + 禁止画面 + 风险条）、亮度调校总则（顺序表 + 锚点网格 + 冲突条）、灰度链路步骤、检测项速查表、型号 × 阶段矩阵、现场问答条、标准流程步骤卡（圆角序号 + 步骤配图网格 + 「手册原文 →」）、坑位条、案例卡片、图片网格与灯箱、页脚。

**适配**：深色模式跟随系统变量；`@media print` 隐藏侧栏 / 顶栏、去卡片边框；≤900px 转单列，导航移到正文上方且列表限高滚动；灯箱内 `Esc` 与点击空白均可关闭。

**版本可见性**：`index.html` 的 CSS / JS 引用统一带 `?v=1.2`，与 `knowledge.js` 的 `meta.version` 保持同号；顶栏品牌旁渲染 `调试速查 v1.2`，页脚渲染 `速查 v1.2（数据更新 2026-11-10）` 并把 `meta.rev` 放进 `title`。改完数据只需同步版本号（`index.html` 五处 + `meta.version`）即可让现场浏览器绕过本地缓存，现场也能凭这两处文字判断手上是不是最新版。

## 10. 内容口径（写进数据的规则）

- **区间必带步长**：参数一律"合理区间 + 步长 + 调整方向"，例如 `AI 置信阈值 0.50 ~ 0.75（±0.05）`，禁止只写单值。
- **阶段数随机型变化**：端面 8 工位为主相机 3 阶段 + 跑马灯 3/4 独立相机；6 工位为 4 阶段 / 9 张，频闪并入端面相机。任何"阶段 N"的表述都必须能对上机型。
- **先定位再检测**：所有工位都强调"阶段一定位 → 后续阶段共享坐标"，定位失败优先于参数调整。
- **红线不参与调参**：存图模式、双算法冗余、校准流程等写进 `redlines` 与专题，不放进参数表，避免被当成"可调项"。
- **口径冲突以实测为准**：手册数值与设备实测冲突时，在 `meta.note` 与对应参数说明里显式标注。
- **亮度写"判据 + 读数"，不写"抄数字"**：手册未给出各阶段的绝对曝光 / 光源百分比（出厂已标定），因此每个阶段写 `anchor`（可核对的画面判据）、`tune`（先动谁、后动谁、改完怎么复测），整套口径放在 `teach.brightness`。禁止把别条线的数值当成标准值抄录。
- **冲突显式落地**：手册自身前后矛盾处（内径滤波核 5×5 允许/禁止、灰度阈值方向随二值化模式反转、保持架 4.x 编号与运行阶段不符、防尘盖 3.3 名为"阶段二盖子模型"）统一收录到 `teach.brightness.conflicts`，每条给出"现场照哪条执行"，并保留手册条款号。
- **流程照抄步序、图只用手册原图**：每个工位的标准化调参流程（`teach.flow`）严格按手册 5.6 / 6.7 / 7.7 的步数与步名落地，不合并、不增删步；配图一律取手册原图（欠曝 / 过曝 / 合格像、界面截图），逐张写清"这张图说明什么"，不另画示意图，避免"图不是现场样子"。

## 12. 已知限制

1. **静态数据**：无后台，知识层改动需人工提交；不适合多人同时编辑。
2. **抽取非无损**：合并单元格、文本框、复杂编号可能失真；条款级细节以 docx 原件为准。
3. **搜索能力有限**：子串 + AND，无分词、无同义词、无拼音；"暗斑 / 脏点"这类近义词需分别命中。
4. **无使用统计**：不知道哪些页面被看得多，内容优先级靠人工判断。
5. **移动端表格**：宽表格横向滚动，未做卡片化改造。
6. **教学只到 P0**：无情景决策树（漏检 / 误判的逐步选择与跳步扣分，P1）、无参数沙盘（改参数看成像 / 判定变化，P2）；题型目前全为单选；单课题目多（如 7.8 字符与宽度 56 题）时按 12 题抽样练，尚未做"错题优先"的智能组卷。
7. **进度不跨机器**：`localStorage` 随浏览器清缓存丢失，需手工导出 / 导入 JSON；无账号体系，因此无法做班组看板。
